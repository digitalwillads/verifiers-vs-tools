The line between a verifier and a tool

A verifier answers one question: is this right for the business? To answer it, the verifier needs true data. Getting true data is the tool's job. When a tool cannot read something, it should say so plainly. The verifier then says it could not judge. It never passes, and it never grows a rule to patch the read.

A verifier judges

  • Is this change right for this account and its targets?
  • Does the issue really exist, with the right numbers?
  • Does an email to a client say only true things?

A tool reads

  • Every mailbox the client writes to.
  • A client's last three calls, from any recorder.
  • Account data, pages and tasks, with a clear "could not read" state.

Neither one polices the AI's paperwork

Semicolons in audit text, citations between log lines and CRM read-back rows are not business logic. Rules like these made each new output (stories on Oct 15, the CRM step on Oct 16) bring new checks, then false alarms, then more fixes.

The 10 business-logic rules stay

These judge the account itself, so they fit a verifier's job. Each one fixed a wrong answer. Two examples: the audit advised manual bidding for Performance Max, which Google does not allow. It also told the agent to add keywords to a Shopping ad group. Will kept all 10.

What changed today

  • Client runs, the A&R check-in and the Verifier audit never change a verifier. They fix their own work to pass. After 3 tries, they skip the item and log it (Barbara v796, PR #58).
  • A Claude Code hook, run-no-verifier-builds, blocks gate work, cargo, verifier code edits and forks inside those runs.
  • A run logs each new verifier miss in one queue: verifiers/data/clients/dwa/verifier-misses.md. Will picks what gets built. A fresh session builds only setup and safety entries.
  • The 23 reading and paperwork rules are coming out of the verifiers now. When one of the old false alarms comes back, a run logs it and moves on.
